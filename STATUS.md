## Now
Daily Bhagavad Gita shloka site live at geetasar.com (static, zero-backend, Cloudflare Pages) with shareable 1080×1080 cards. GA4 is firing `card-share` / `card-download` / `link-copy`, so share traction is measurable. Sveltia CMS runs at `/admin/`, authoring theme entries into `content/themes/`. **The verse text itself is now editable there too.** `content/verses/` — 701 files, one per verse, carrying the full Sanskrit, transliteration, Hindi and English — is the single source of truth; `data/verses.json` and `tools/build-verse-index.js` are deleted, because two copies of the same data with no sync mechanism is how they drift apart. `build.js` assembles the files in memory (and into `dist/verses.json`) at build time, so `card.js`, the daily verse and every rendered page are untouched — all 1,425 generated files are byte-identical to before the split. The assembly sorts **numerically by chapter then verse** and derives each verse's numeric id from its position: alphabetical filename order would give 1-1, 1-10, 1-100 and silently reshuffle the daily verse for every reader, so that sort is the load-bearing line in `lib/verses.js`. `tools/validate-verses.js` gates it — FAIL on an emptied `sa`/`en`, c/v not matching the filename, a duplicate verse or a count other than 701; WARN as a correction worklist, which today names the three known defects in the public-domain dataset (1.7 and 16.6 both read "No changes needed.", 11.19 has Devanagari in the transliteration column). `hinglish()` moved to `lib/hinglish.js` so the validator and the build share it; Hinglish is still generated from `hi`, never stored. `build.js` turns every `published: true` theme into a `/theme/{slug}/` page plus a grouped index at `/themes/`. **The thematic layer is now hardened for the long haul, on the premise that themes get authored one at a time over years and every theme URL is a permanent public commitment.** The canonical slug rule lives in exactly one place (`canonicalSlug()` in `lib/slug.js`) and is enforced twice — in the build, and as a `pattern:` on the CMS id field copied verbatim from the same constant, with the validator warning if the two ever drift. Multilingual fields migrated from flat `label_en`/`label_hi` to nested `{ en, hi }` objects, so adding Tamil later is one entry in `LANGS` plus one CMS subfield rather than new fields on every theme file; only `en` is required and everything else falls back to English at build time. `tools/validate-themes.js` runs immediately after the verse gate in `node build.js` and **exits 1 without writing anything** on a duplicate slug, a dangling verseId, an unknown type, malformed JSON, or a published theme missing its label, intro or third verse — structural rules bind drafts too, quality rules only bind on publish. A third code zone appeared alongside `src/` (copied) and `tools/` (runnable): `lib/` holds Node modules required by both, and the repo is still zero-dependency. `docs/theme-prd.md` is now the source of truth for the theme schema, the slug rules and the editorial standard; `docs/content-log.md` tracks content separately from this file. The CMS theme list now summarises each entry as label — cloud — Image: Yes/No, so the two fields that decide how a theme renders are readable without opening it. The one existing theme was migrated and renamed (`sorrow.json` → `affection.json`, id `"Affection"` → `"affection"`) with its URL unchanged, and every one of the 706 built pages is byte-identical to before. The danda split that breaks single-line shlokas into padas is now generated once in `lib/shloka.js` and attached as `sl` the way `hn` is, so the card, the verse pages, the homepage text and the theme pages can no longer disagree about where a shloka breaks; `card.js` also fits the shloka to the card properly — its size floor is now actually measured, and a composition that wraps into more lines than expected shrinks instead of spilling past the border.
